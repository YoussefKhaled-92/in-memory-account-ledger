# Ambiguities and explicit resolutions

These are assessment-specific choices. They should be challenged during review rather than mistaken for universal banking practice.

1. **Arrival order versus booked date.** E10 is after E9 but booked a day earlier. Process E1-E10 exactly as supplied. `RecordedDay` is the maximum booked day reached; it never rewinds. Preserve supplied BookedDay and ValueDay in the immutable input result.
2. **When a day closes.** Advance to a later booked day by closing earlier days *before* applying its event. Finish closes the last day only after all input, including late E10. A day with several inputs is not prematurely assessed between those inputs.
3. **Backdated fee assessment.** Revisit all already-closed days after a successful input, chronologically. Each assessment itself affects later-day closing balances. This is not one fee per event or simply one fee on the backdated value day. Day 3 stays positive once the earlier fee is included.
4. **Whether to refund fees after reversal.** Retain charges already assessed. Reversal compensates the referenced principal only. The task never mandates automatic fee refund. This deliberately differs from a compensating-refund policy discussed before implementation. A production refund must append its own approved credit; this model does not expose automatic fee-refund behavior. Consequently a restated positive historical close can still show an earlier assessment.
5. **Restated versus as-observed balances.** `Balance` always means value-dated balance from entries known now. Replay output separately preserves observed decisions and an E8 checkpoint. Final daily balances are not claims that staff knew the future on those dates.
6. **Criterion 1's before-fee language.** Accept -370 as the principal-only counterfactual at E8. Actual Day 2 balance by then is -395 after the Day 2 assessment. No rewriting history to make both views equal.
7. **Day 5 versus Day 6 fee decision.** The Day 5 assessment is triggered when the clock advances to Day 6, before E9. Assessing only once after the entire stream would erase the negative view that existed at that close. Recorded day and value day are therefore different fields.
8. **Interest restatement.** Compute final daily accruals once all inputs are known, using final restated balances including retained fees. There are no provisional posted accruals to mutate. A future provisional implementation would require immutable accrual adjustments.
9. **Interest timing and circularity.** Day 6's capitalization is excluded from its own basis. Capitalization is per account and currency, not one combined multi-currency credit. No zero-credit posting for an account with no accrual.
10. **Rounding mode and point.** Use decimal, AwayFromZero; round incoming positive amounts to account precision. Reject nonpositive amounts and positive values rounding to zero. Store signed rounded amounts for debits and reversals. Round each daily accrual, then add exactly. No floating-point epsilon or discarded adjustment.
11. **Equal instalments that are not representable.** Prefer exact conservation over falsely equal rounded parts. Allocate whole minor units with earlier parts taking the remainder; output the exact three postings. Count may exceed units, producing explicit zero parts. Default count is one; only credits use the split count.
12. **Ordinary debits versus authorization restrictions.** The affordability rule applies to holds, not ordinary debits. Ordinary debits and settlement of a previously approved hold can overdraw an account; otherwise E7 could not exercise the stated fee behavior.
13. **Historical authorization decisions.** Decisions use the current recorded-time balance and active holds. Backdating never reapproves a rejected hold or revokes a previously approved one. Settlements do not rerun approval. E8 remains rejected after E9.
14. **Authorization value date.** Retained as input metadata; holds become effective when received and approved, not delayed until a future value date or reconstructed retroactively. `Available` is a current-state query, not a historical available-balance function.
15. **Partial/excess settlement.** Accept a positive amount up to the active hold. Any accepted settlement is terminal and releases all residual hold; no multi-capture support. Excess/zero/unknown/terminal settlements reject without a monetary posting. No off-ledger fallback settlement.
16. **Authorization IDs.** IDs are scoped to the account, unique even after rejection or release. A retry with the identical event ID/payload returns its original result. A fresh event may not resurrect that ID. Cross-account settlement rejects.
17. **Other lifecycle endings.** Explicit Release moves Active to Released, releasing all funds without a ledger entry (merchant cancellation/manual release). Rejected is a terminal application outcome, not termination of an existing active hold. There is no expiry, account-closure release, timeout scheduler or implicit end-of-window cancellation. The red test exposes the missing expiry path.
18. **What can be reversed.** Only a prior credit or debit source event on the same account, once, at its original value day. All instalment postings are reversed together. Unknown, duplicate, settlement, fee, interest, or reversal-of-reversal references reject. Card settlement reversal would need separate lifecycle/product semantics.
19. **BHD overdraft charge.** AED 25 is not BHD 25. No exchange rate or BHD fee is specified. A negative BHD close raises an explicit unsupported-policy error and stops closing; the supplied BHD account never goes negative. A caller can inject a bank-approved BHD policy; no FX conversion is fabricated.
20. **Configuration history.** The supplied policies are immutable for the replay and copy fee configuration at construction. Charges store actual assessed amounts. There is no effective-dated configuration catalog; changing a product requires a new policy instance or implementation, never mutable configuration halfway through history.
21. **Append-only scope.** Input outcomes, postings and lifecycle transitions are immutable records in private append-only lists. Read-only snapshots prevent caller mutation. Derived grouping/temporary calculation lists are not financial records. This is not tamper-evident durable storage.
22. **Failure categories and transactions.** Customer/business validation errors are recorded and have no monetary effect, though a declined authorization appends its Rejected decision. Invalid day/blank/reserved/conflicting IDs, finalization violations, unsupported financial policies, resource exhaustion and arithmetic overflow are caller/configuration/runtime faults. They abort explicitly. Previously valid fees can already have been assessed at a time boundary; there is no rollback or durable cross-operation transaction. Custom policies must be deterministic, side-effect-free and valid for every applicable account/day.
23. **Input finality.** Finish is idempotent and freezes the six-day window; new events then reject, while exact retries still return the old result. Late inputs within the stream are allowed; reopening after capitalization is out of scope.
24. **General ledger and concurrency.** Signed account deltas model customer balances; there is no bank contra-account, FX position, double-entry balancing, multi-writer serialization, working-day calendar, timezone cutoff or persistence. Single writer and integer business-day window are explicit scope limits.
25. **The required failing test.** Run the default green suite for regression; run `--known-failure` to include the genuinely failing expiry probe. It asserts a production capability our model intentionally lacks, not a false monetary expectation. Both modes are documented and verified.
