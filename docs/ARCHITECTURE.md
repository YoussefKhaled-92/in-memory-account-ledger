# Architecture & trade-offs

Implementation note: this document describes the actual single-writer C# core, not a proposed bank platform. References are to code responsibilities, not a repetition of the replay or its rules.

## 1. Append-only at scale

The implemented Clean Architecture separates Domain (business records, reservation/reversal invariants and financial policies), Application (use cases, projections and journal port), and Infrastructure.InMemory (append-only histories and sequence allocation). Core composes these through Microsoft.Extensions.DependencyInjection; Replay owns scenario data and reporting. Each `AccountLedger` owns a disposable provider, with journal, session and use cases registered as per-provider singletons. Separate ledgers share no internal mutable state. Caller-supplied policies/handlers remain caller-owned. Constructor injection and inward dependencies remain: Application references Domain; Infrastructure implements the application's port. Neither inner layer references the container.

Operation dispatch uses Strategy plus an explicit Registry. Each operation has an `IEventHandler`; `EventHandlerRegistry` maps its named `EventKind` to that use case. New client kinds register at composition without changing a switch or the coordinator. Duplicate registrations fail at startup. `ProcessEvent` retains arrival order, identity checks and day boundaries; `FinalizeLedger` retains the final-input watermark. `LedgerQueries` derives balances and reservation state synchronously. This separation adds files and wiring, but keeps calculations, lifecycle rules and orchestration independently understandable. The model remains single-writer; the registry adds no isolation or rollback.

For fixed accounts and window, CPU will probably become visible before storage at 100x input volume; this is an inference, not a benchmark. Balance queries scan postings, input processing scans prior outcomes, and authorization queries regroup history. Closing repeatedly searches assessments. Roughly, each fee pass is O(A*D*(J+F)); repeated across N arrivals it can approach O(N*A*D*(J+F)). Growing histories can make replay quadratic. Port reads return snapshots, adding allocations; this refactor claims no speedup. A long horizon increases D too, so input count alone understates the cost.

The cheapest first change is rebuildable indexes: event ID to outcome; account/authorization ID to latest transition; account/day to assessment; account/value-day to aggregated posting deltas. Prefix totals or periodic balance checkpoints bound common queries. Backdating invalidates/rebuilds the suffix from its earliest affected day; it must not update an old journal record or reuse a stale checkpoint. Preserve a sequence watermark so derived state can be reconciled against the authoritative append order. These indexes reduce scans but add consistency work and memory; they do not solve retention.

Unbounded state lives in all five history lists, plus any permanent idempotency index and unresolved holds. Final accrual storage grows with accounts times horizon; caller-retained snapshots can multiply memory. After indexing, partition the journal by account/time, archive sealed segments to durable storage and retain bounded hot checkpoints. Keep cold records retrievable for audit and legally required retention. Never compact away reversals, declines or original approvals merely because their current monetary effect is zero. This migration needs crash-safe append/checkpoint transactions; adding a cache alone does not create recoverability.

## 2. Value-dated entries in production

The implementation separates supplied booking day, effective value day, recorded high-water day and append sequence. Restated balances answer a different question from what staff or an authorization service knew at an earlier time. Retaining both views matters for disputes, statement corrections, interest remediation, reconciliation to payment rails and finance reporting. Reversing principal does not itself authorize a fee refund; the retained-fee choice needs contractual and compliance approval before production. A commercial decision to reimburse must append a distinct approved adjustment.

Regulatory context: the CBUAE Consumer Protection Standards require disclosure of fee schedules (2.1.1.18), secure consumer-record retention for a minimum five years with specified relationship/transaction triggers (6.1.6.1), limits on unnecessary retention (6.1.6.2), and UAE storage plus a separate secure backup for consumer/transaction data (6.1.6.3). These are obligations around this system's records and customer treatment, not a rule that prescribes our particular backdating algorithm. The bank's compliance team must assess applicable amendments and other retention/reporting obligations. [1]

My go-live control is a mandatory maker-checker gate for value dates earlier than the current business day. Before append, the maker submits reason, source evidence, effective date and an impact preview of affected balances, charges, interest and issued statements. A separate authorized checker approves a versioned decision; otherwise no posting occurs. Record both identities, timestamps and the immutable before/after impact reference. Escalate closed accounting periods rather than quietly reopening them. This is a proposed control, not a claim that the cited standard mandates this exact workflow.

An accepted correction should enqueue idempotent downstream reconciliation and customer remediation work. Finance must define period locks, reporting cutoffs and corrected-statement handling; fraud/AML monitoring should receive both effective and arrival timestamps so backdating cannot conceal when activity was actually observed. Product owners must approve correction windows and fee-refund semantics. A complete production design also needs durable sequencing, timezones/calendars, auditable access and retention/legal-hold handling; an in-memory sequence and integer day cannot supply them.

## 3. Authorization lifecycle

The implemented transition log has Active, Settled, Released and Rejected outcomes. Latest state is a projection; earlier decisions remain untouched. Terminal partial settlement releases unused funds and forbids a second capture. Previously granted approval survives subsequent value-date restatement; a declined request is never silently retried after funds improve.

Every non-settlement ending supported by this model is explicit Release. A merchant cancellation, abandoned purchase reported by the merchant, or bank-authorized manual cancellation uses the same active-to-released command. The command releases the whole hold without a monetary posting. It requires the same account and existing active authorization; a repeat with the same event ID is idempotent, while a new event against a terminal hold rejects. Production must authenticate the sender, require a reason and authority for manual release, and emit an auditable customer-availability update. Account closure is not a separate implemented ending and does not implicitly invoke Release.

Rejected is a terminal authorization-request outcome when funds are insufficient, not the ending of an already-active hold. No funds were held and no debit is created. The rejection reason and original decision survive; a funded retry requires a fresh authorization identity. This distinction avoids calling a rejected request a released reservation.

There are no other active-hold endings here: no automatic expiry, implicit end-of-window release, account-closure transition, incremental authorization, or timeout task. The required red test demonstrates the consequence: an orphaned approved hold remains active after finalization. This is an admitted production gap, not a skipped assertion or an invented deadline.

Before production, add product/network-specific deadlines and an immutable Expired transition, processed idempotently with atomic release of the reservation. Expiry and settlement must compete through the same per-account transaction boundary so only one wins. Define late presentment explicitly: do not silently resurrect an expired hold; route it through a separate permitted presentment/exception flow. Account closure must resolve or transfer outstanding reservations under an approved workflow. Transport timeout alone is not evidence that a merchant cancelled a transaction; reconciliation must determine the authoritative outcome.

## 4. What I cut and why

- **Durability and a full general ledger:** customer-account signed deltas keep the exercise small. Deferred risk: process loss destroys state and missing contra-accounts cannot reconcile bank-wide assets/liabilities. Add a transactional durable journal, backups and balanced postings before real money.
- **Multi-writer execution and distributed atomicity:** one caller owns the ledger. Deferred risk: racing approvals overspend; posting, outcome and projection may diverge on a crash. Use serialized per-account commands and atomic journal/projection/outbox commits. This core has no rollback boundary for policy/runtime faults.
- **Policy catalog and recovery orchestration:** injected policy instances are fixed for one replay and must be deterministic; caller-owned custom policies are not cloned. Interest is prepared for all accounts before capitalization, but the whole fee/input/finalization workflow is not a durable transaction. Deferred risk: a custom policy fault or decimal/resource limit interrupts processing after earlier valid work. Add preflight validation, bounded inputs, versioned effective policies and restartable batch IDs.
- **Full temporal model and incremental restatement:** integer business days, full scans and an explicit final-input watermark make behavior inspectable. Deferred risk: cutoff/DST mistakes, slow backfills, or a correction after capitalization requiring reopening. Add actual timestamps, business calendars and versioned correction/accrual-adjustment jobs.
- **Automatic fee refunds and universal currency support:** retained assessments and an explicitly missing BHD overdraft policy avoid guessing product terms or FX. Deferred risk: incorrect customer treatment or an unsupported negative-currency close. Obtain approved per-currency policies and implement explicit compensating remediation.
- **Complete card lifecycle:** one terminal capture and explicit whole-hold release avoid partial-capture bookkeeping. Deferred risk: stranded funds, delayed-presentment losses and unsupported merchant patterns. Expiry, multi-capture and settlement reversal need distinct audited operations, not ordinary credit/debit reversal.
- **Security and operations:** no identity/permissions layer, encryption, immutable archive, reconciliation service, alerts, retention engine, real payment integration or regulatory reporting pipeline. Deferred risk: unauthorized changes, fraud, disclosure failures and inability to demonstrate recovery. Add these outside the pure core with clear ownership and control evidence.
- **Test infrastructure and performance claims:** the dependency-free harness retains the original assertions and real failing expiry probe. A complete-history fixture captured before refactoring guards input-boundary ordering; extension and policy-failure tests exercise new seams. These complement independent monetary assertions rather than replace them. Framework discovery, standard result export, load/concurrency tests, crash recovery tests and independent audit remain absent. A passing regression suite does not establish production readiness.
